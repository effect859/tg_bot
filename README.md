# tg-bot

Telegram-бот для генерации студенческих документов. Первый коммерческий сценарий —
**отчёт по практике в DOCX**.

Текущее состояние: регистрация пользователей, главное меню, оформление заказа с
приёмом материалов (PDF, DOCX, TXT), извлечением из них текста, анализом
материалов через LLM (Anthropic) — черновик ТЗ, уточнением недостающих данных и
подтверждением ТЗ, составлением плана отчёта через LLM и подтверждением плана.
Подтверждённый план фиксирует цену заказа в кредитах. Кредиты покупаются за
Telegram Stars и списываются кнопкой «Оплатить», после чего начинается генерация
текста отчёта, сборка DOCX, завершение заказа (файл в хранилище, `COMPLETED`) и
доставка готового DOCX пользователю (автоматически и кнопкой в «Мои заказы»).
Если отчёт после оплаты подготовить не удалось, кредиты автоматически возвращаются
на баланс, а заказ отменяется. Возврат Stars, ручной разбор отвергнутых платежей,
OCR и очередь задач не реализованы.

## Требования

- Python 3.12+
- Docker Desktop (для PostgreSQL и Redis)
- Токен бота от [@BotFather](https://t.me/BotFather)
- Ключ API Anthropic (`ANTHROPIC_API_KEY`): без него бот не запускается

## Локальный запуск

PowerShell (Windows):

```powershell
# 1. Виртуальное окружение и зависимости
python -m venv .venv
.venv\Scripts\Activate.ps1
pip install -e ".[dev]"

# 2. Настройки: скопируйте пример и впишите BOT_TOKEN
Copy-Item .env.example .env

# 3. PostgreSQL и Redis
docker compose up -d

# 4. Миграции
alembic upgrade head

# 5. Бот
python -m app.main_bot
```

В bash/zsh отличаются только активация окружения (`source .venv/bin/activate`)
и копирование файла (`cp .env.example .env`).

## Тесты и линтер

```powershell
docker compose up -d      # тестам нужен PostgreSQL
pytest
ruff check .
ruff format --check .
```

Тесты работают на отдельной БД `tg_bot_test` (создаётся `docker/postgres/init.sql`
при первом запуске контейнера). Перед прогоном схема пересоздаётся миграциями
(`downgrade base` → `upgrade head`), каждый тест выполняется в транзакции, которая
откатывается. `tests/test_migrations.py` проверяет, что модели и миграции не расходятся.

> Если том `postgres_data` был создан до появления `init.sql`, тестовой БД не будет.
> Создайте её вручную:
> `docker compose exec postgres createdb -U tg_bot tg_bot_test`

## Миграции

```powershell
alembic revision --autogenerate -m "описание"   # после изменения моделей
alembic upgrade head
alembic downgrade -1
```

Сгенерированную миграцию всегда просматривайте вручную. Новое значение
PostgreSQL enum (например, новый тип документа) добавляется миграцией с
`ALTER TYPE ... ADD VALUE`.

Тесты извлечения текста стоит прогонять и в Linux-контейнере (это целевая среда;
версии libxml2 в колёсах lxml для Windows и Linux разные, и коды ошибок у них
тоже). Из каталога проекта, при запущенном `docker compose up -d`:

```bash
docker run --rm --network tg_bot_default -v "$PWD:/src:ro" python:3.12-slim bash -c '
  cp -r /src /work && cd /work && rm -rf .venv &&
  pip install -q -e ".[dev]" &&
  TEST_DATABASE_URL=postgresql+asyncpg://tg_bot:tg_bot@postgres:5432/tg_bot_test pytest -q'
```

## Production Packaging & Runtime

Сборка и запуск бота в Linux-контейнерах (`Dockerfile`, `docker-compose.prod.yml`).
Это упаковка: запуск с реальными Telegram- и Anthropic-ключами — отдельный этап.

**Образ** (`Dockerfile`, Python 3.12-slim, пользователь `app`, не root):

```bash
docker build --target runtime -t tg-bot:runtime .   # production
docker build --target test -t tg-bot:test .         # полный pytest в Linux
```

В образ попадают только `pyproject.toml`, `README.md`, `alembic.ini`, `alembic/`,
`src/` (и `tests/` — только в стадию test): остальное отсекает `.dockerignore`, в том
числе `.env`, `.git`, `.venv`, `var/`. Секретов в образе нет.

**Production-стек** (`docker-compose.prod.yml`): `postgres`, `redis`, одноразовый
`migrate` (`alembic upgrade head`) и `bot`. Бот стартует только после успешного
завершения `migrate`; если миграция упала, бот не запускается.

```bash
docker compose -f docker-compose.prod.yml --env-file /путь/к/prod.env up -d --build
```

- **Окружение.** Обязательны `BOT_TOKEN`, `ANTHROPIC_API_KEY`, `POSTGRES_PASSWORD` —
  без них `docker compose` не соберёт конфигурацию. По желанию: `POSTGRES_USER`,
  `POSTGRES_DB`, `LLM_MODEL`, `LOG_LEVEL`, `EXTRACTION_MEMORY_LIMIT_MIB`,
  `HEARTBEAT_INTERVAL_SECONDS`, `HEARTBEAT_MAX_AGE_SECONDS`. `DATABASE_URL` и `REDIS_URL`
  собирает compose-файл (пароль со спецсимволами в URL нужно URL-кодировать).
- **Тома.** `postgres_data` (БД), `redis_data` (FSM диалогов), `bot_storage`
  (`/app/var/storage`: материалы и готовые отчёты).
- **Сеть.** Наружу не публикуется ни один порт: PostgreSQL и Redis доступны только
  контейнерам стека. Бот работает через polling — входящих соединений не нужно.
- **Проверка схемы.** Перед polling бот сравнивает ревизию БД с head миграций
  (`app/db/schema.py`, только чтение). При несовпадении — ошибка в лог («run `alembic
  upgrade head`») и выход с кодом 1; миграции сам бот не выполняет.
- **Healthcheck.** Бот раз в `HEARTBEAT_INTERVAL_SECONDS` выполняет `SELECT 1` и
  атомарно обновляет метку `HEARTBEAT_PATH` (`app/services/heartbeat.py`; в метке только
  время). Docker `HEALTHCHECK` запускает `python -m app.healthcheck`: код 0 — метка
  свежее `HEARTBEAT_MAX_AGE_SECONDS`, 1 — устарела, повреждена или её нет (процесс
  завис или БД недоступна). Healthcheck не требует БД, Redis и сети.
- **Отличие от `docker-compose.yml`.** Dev-файл поднимает только PostgreSQL и Redis на
  `127.0.0.1` с паролем `tg_bot` и базой для тестов; бот при разработке запускается
  из venv (см. «Локальный запуск»). Dev-файл не меняется.
- **Бэкапы.** Резервное копирование и восстановление БД и хранилища не реализованы —
  отдельный будущий этап.

**Тесты в Linux.** Стадия test запускает полный pytest в Linux (в том числе тесты,
которые на Windows пропускаются, например лимит памяти `RLIMIT_AS`). База — PostgreSQL
из `docker-compose.yml`; контейнер подключается к сети dev-стека напрямую:

```bash
docker compose up -d
docker run --rm --network tg_bot_default \
  -e TEST_DATABASE_URL=postgresql+asyncpg://tg_bot:tg_bot@postgres:5432/tg_bot_test tg-bot:test
```

Не используйте `host.docker.internal`: тесты открывают тысячи коротких соединений, и
через NAT Docker Desktop подключения изредка не устанавливаются за 60 с. Linux-прогон
и обычный pytest на хосте нельзя запускать одновременно — у них общая база.

## Извлечение текста из материалов

После приёма файла бот в том же апдейте извлекает из него текст и сообщает
результат отдельным сообщением. То, что там не удалось или не случилось,
подбирает восстановление (см. ниже) — без участия пользователя.

- **Изоляция.** Разбор выполняется в отдельном дочернем процессе
  (`python -I -m app.extraction.worker`) с минимальным окружением: секретов бота
  в нём нет. Жёсткий тайм-аут 30 с, после него процесс снимается и дожидается
  завершения; stdout читается с потолком 8 МиБ. Одновременно работает один процесс.
  На Linux процессу ставятся `RLIMIT_AS` (`EXTRACTION_MEMORY_LIMIT_MIB`, по
  умолчанию 1024 — экспериментальное значение) и `RLIMIT_CPU` 35 с; на Windows
  ограничения памяти нет.
- **PDF** — pypdfium2 (PDFium). **DOCX** — lxml, без python-docx. **TXT** —
  UTF-8, UTF-16 с BOM, cp1251.
- **Лимиты:** 500 000 символов на материал; первые 300 страниц PDF; мягкий бюджет
  20 с (дальше — частичный результат); DOCX: одна XML-часть до 16 МиБ, всего
  распаковывается не больше 64 МиБ, частей в архиве не больше 1000, сумма
  заявленных размеров не больше 256 МиБ.
- **Хранение.** Текст — в `order_material_texts` (NFC, переводы строк `\n`,
  страницы PDF разделены `\f`). У материала: статус, машиночитаемая причина
  сбоя `failure_reason`, число попыток, момент начала обработки.
- **Пустой текст — не ошибка:** материал обрабатывается с пометкой «текста нет».
  «Похоже на скан» (на странице только изображения) и «текст может быть
  извлечён неверно» — эвристики, а не причины отказа.
- **Повторы** — только для временных сбоев (хранилище, запуск процесса,
  прерванная обработка, временная ошибка БД при сохранении результата), не больше
  3 попыток; попытка расходуется только при взятии материала в обработку.
  Повреждённый, зашифрованный файл, тайм-аут, аварийное завершение и отказ БД
  принять результат не повторяются: пользователь присылает файл заново. Файл
  материала обработка только читает и при сбоях не трогает.
- **Ошибки БД при сохранении результата** классифицируются по SQLSTATE
  (`app/db/errors.py`): ошибки данных, ограничений и лимитов (`22*`, `23*`, `54*`)
  — `result_rejected`, без повтора; соединение, deadlock, сериализация, нехватка
  ресурсов, тайм-аут запроса и нераспознанные ошибки — `database_error`, с
  повтором. Код и тип ошибки сохраняются в `processing_error` (без текста документа).

### Восстановление обработки

Внутри процесса бота работает проход восстановления
(`app/services/material_recovery.py`): первый — сразу при запуске, дальше раз в
60 с (`RECOVERY_INTERVAL_SECONDS`), не больше 10 материалов за проход
(`RECOVERY_BATCH`), начиная с самых старых. Он берёт материалы заказов, которые ещё
принимают файлы:

- `RECEIVED` старше 2 минут (`RECEIVED_GRACE`) — свежие обрабатывает сам апдейт;
- `PROCESSING` дольше 3 минут (`STALE_PROCESSING_AFTER`) — прерванная обработка;
  после рестарта более свежий `PROCESSING` не трогается, пока порог не истечёт;
- `FAILED` с повторяемой причиной, пока не исчерпаны попытки.

Материал обрабатывается тем же кодом, что и в апдейте; двойной захват исключают
блокировка строки и номер попытки. Очередь извлечения общая: если она занята,
проход заканчивается и продолжается в следующем. Срок обработки не гарантируется —
при большом числе материалов они ждут очереди. Пользователь получает сообщение об
окончательном исходе (текст извлечён или повтора не будет) после фиксации в БД,
не больше одного раза; если процесс упадёт между фиксацией и отправкой, сообщения
не будет. Интервал и размер прохода — константы в коде, не настройки.

### Завершение приёма материалов

Файлы принимаются только на шаге «ожидает материалы» (`WAITING_FOR_FILES`). В
ответе о принятом файле и в напоминании о загрузке есть кнопка «Материалы
загружены»: она переводит заказ к анализу материалов (`ANALYZING_MATERIALS`), если
материалы готовы (`check_materials_ready` в `app/domain/materials.py`):

- есть хотя бы один материал;
- обработка всех материалов завершена: нет `RECEIVED`, `PROCESSING` и `FAILED`,
  который ещё будет повторён; окончательные сбои переход не блокируют;
- хотя бы из одного материала извлечён непустой текст (обработанный файл без
  текста — скан или изображения — не считается).

Проверка и переход выполняются под блокировкой заказа (`finish_materials`): новый
файл не может добавиться между проверкой и фиксацией, а после перехода файлы
отклоняются. Повторное и устаревшее нажатие ничего не меняет. Пользователь получает
итог: сколько файлов, из скольких извлечён текст, какие не обработаны и почему —
без технических подробностей. Затем начинается анализ материалов (см. ниже).

Ограничения полноты:

- нет OCR: из сканов и картинок текст не извлекается;
- DOCX: не извлекаются сноски, концевые сноски, комментарии, SmartArt и
  диаграммы; текст надписи выводится перед абзацем, в котором она стоит;
  документы с `DOCTYPE` отклоняются;
- PDF: многоколоночная вёрстка читается построчно поперёк колонок; разделение
  «скан» и «шрифт без ToUnicode» — эвристика;
- обработка рассчитана на один экземпляр бота (polling). При нескольких
  экземплярах один материал дважды не захватывается (блокировки строк в
  PostgreSQL), но у каждого экземпляра своя очередь и свой дочерний процесс
  извлечения: одновременно может работать по процессу на экземпляр;
- прерванная обработка (например, рестарт во время извлечения) расходует попытку:
  частые рестарты могут исчерпать 3 попытки.

Лицензии встроенных библиотек — в [THIRD_PARTY_NOTICES.md](THIRD_PARTY_NOTICES.md).

## Анализ материалов (черновик ТЗ)

После завершения приёма бот анализирует извлечённые тексты через Anthropic
(`app/services/requirements_analysis.py`, модель — `LLM_MODEL`, по умолчанию
`claude-sonnet-5-5`) и создаёт черновик ТЗ v1. Модель только предлагает значения
полей; что принять, чего не хватает и куда перейти дальше, решает код
(`app/domain/requirements.py`).

- **Структурированный ответ.** Запрос с `output_config.format` (JSON Schema): по
  каждому полю — значение и дословная цитата из материалов. Серверный запасной
  вариант модели не включён.
- **Проверка.** Значение принимается, только если оно проходит проверку (формат
  дат, длина, диапазон), его цитата (от 10 символов) есть в отправленном модели
  тексте и сама цитата подтверждает значение: текст входит в цитату дословно (без
  учёта регистра), в цитате та же дата (`YYYY-MM-DD` или `DD.MM.YYYY`) или то же
  число страниц. Пробелы и переводы строк нормализуются; морфологии и нечёткого
  сравнения нет. Иначе поле считается ненайденным.
- **Персональные данные.** ФИО студента, вуз и руководитель у модели не
  запрашиваются — их спросят у пользователя. Сами материалы могут содержать
  персональные данные и уходят модели как есть: минимизация данных — отдельная
  задача до публичного запуска.
- **Объём.** Не больше 400 000 символов текста материалов на попытку: материалы
  целиком по порядку загрузки, пока помещаются, следующий — частично, остальные
  не включаются. Об этом пишется в лог и сообщается пользователю.
- **Итог.** Обязательные поля (тема, вид, место и даты практики, вуз, ФИО
  студента) не найдены — заказ переходит к уточнению данных
  (`WAITING_FOR_MISSING_DATA`), все найдены — к подтверждению ТЗ. Вуз и ФИО из
  материалов не извлекаются, поэтому сейчас заказ всегда идёт к уточнению данных:
  первый вопрос приходит вместе с итогом анализа.
- **Повторы.** Не больше 3 попыток за запуск. Временная ошибка (лимиты, сбой
  сервера, сеть, обрезанный или невалидный ответ) — повтор в проходе
  восстановления; постоянная (запрос, ключ, модель, отказ модели) или исчерпание
  попыток — шаг «ошибка» с кнопками «Повторить анализ» и «Отменить заказ». На
  заказ — не больше 9 вызовов модели с учётом перезапусков (считаются по
  `llm_calls`, в том числе прерванные). Повторы SDK выключены (`max_retries=0`),
  поэтому 9 вызовов — это не больше 9 HTTP-запросов к Anthropic.
- **Тайм-аут.** 300 с на запрос — с запасом для большого входа (до 400 000
  символов) и `max_tokens=16000`. Значение будет дополнительно проверено первым
  живым вызовом API.
- **Конкурентность.** Захват шага и сохранение результата — короткие транзакции
  под блокировкой заказа (`orders.step_attempts`, `orders.step_started_at`); во
  время вызова модели транзакция не открыта. Второй одновременный запуск получает
  «уже выполняется»; результат устаревшей попытки (отмена заказа, попытку признали
  зависшей) отбрасывается.
- **Восстановление.** Фоновый проход: первый — при запуске, дальше раз в 60 с, до 5
  заказов за проход. Берёт заказы, ждущие повтора, и попытки дольше 10 минут; заказ
  моложе минуты не трогает — его анализирует апдейт кнопки.
- **Учёт.** Каждый вызов модели — строка `llm_calls` (шаг, модель, токены,
  задержка, статус, код ошибки — без текста материалов). Стоимость в долларах
  пока не рассчитывается.

## Уточнение и подтверждение ТЗ

Недостающие обязательные данные бот спрашивает по одному
(`app/bot/handlers/requirements_dialog.py`, `app/services/requirements_dialog.py`,
правила — `app/domain/requirements_dialog.py`).

- **Без FSM.** Текущий вопрос — первое незаполненное поле из `REQUIRED_FIELDS`
  в черновике ТЗ; отдельного состояния нет. После рестарта бота, `/start` или
  спустя дни диалог продолжается с того же вопроса. Необязательные поля
  (руководитель, группа и т. п.) не спрашиваются.
- **Ответ.** Обычный текст в личном чате принимается как ответ, только если
  активный заказ ждёт данных. Команды, кнопки меню и сообщения из групп
  обработчик не получает (роутер подключён последним). В других шагах — напоминание
  о текущем шаге, ничего не записывается. Изменение отправленного сообщения не
  учитывается.
- **Проверка.** Пробелы нормализуются; пусто, больше предела (тема — 500,
  остальное — 255 символов), меньше двух букв, невидимые и управляющие символы,
  цифры в ФИО — отказ с тем же вопросом и подсказкой. Даты — только `ДД.ММ.ГГГГ`
  (день и месяц можно одной цифрой), 2000–2100 годы; хранятся в ISO. Если дата
  начала оказалась позже даты окончания, обе очищаются и спрашиваются заново.
  Смысл текста не проверяется: каждый принятый ответ повторяется пользователю,
  а перед подтверждением показывается резюме.
- **Подтверждение.** Когда всё заполнено — резюме ТЗ (данные экранированы,
  не длиннее 4096 символов) и кнопки «Подтвердить ТЗ», «Изменить», «Отменить
  заказ». «Изменить» очищает выбранное обязательное поле (даты — обе) и снова
  задаёт вопрос. Подтверждение делает черновик v1 неизменной версией и переводит
  заказ в `PREPARING_PLAN`; кнопка под устаревшим резюме (ТЗ изменилось после
  него) не срабатывает. Сразу после подтверждения начинается составление плана (см.
ниже); заказ до оплаты можно отменить.
- **Один черновик.** Ответы и изменения пишутся в тот же черновик ТЗ, новые
  версии не создаются.
- **Конкурентность.** Ответ, изменение, подтверждение и отмена блокируют строку
  заказа и выполняются по очереди. Два быстрых ответа подряд записываются в два
  вопроса по порядку — ошибку видно в подтверждении ответа и в резюме.
- **Персональные данные.** Тексты ответов (в том числе ФИО) не пишутся в лог.

## План отчёта

После подтверждения ТЗ бот составляет план отчёта через Anthropic
(`app/services/plan_generation.py`, правила — `app/domain/plan.py`) и сохраняет его
черновиком плана v1, привязанным к подтверждённой версии ТЗ. Шаг устроен как анализ
материалов: захват попытки и сохранение — короткие транзакции под блокировкой
заказа, вызов модели — без транзакции.

- **Вход модели.** Поля подтверждённого ТЗ: тема, вид, место и сроки практики,
  специальность, объём, дополнительные требования. ФИО студента, вуз, руководитель
  и группа, Telegram ID, номер заказа и имена файлов модели не передаются. Тексты
  материалов — с тем же лимитом 400 000 символов и тем же тегированием, что при
  анализе; промпт прямо говорит модели, что ТЗ и материалы — данные, а не
  инструкции. Персональные данные внутри самих материалов уходят модели как есть.
- **Ответ.** JSON Schema из двух уровней (разделы и подразделы, без рекурсии):
  название, описание, требования, примерный объём. Код проверяет: 3–15 разделов, не
  больше 10 подразделов у раздела, название 1–200 символов, описание до 1000, до 10
  требований по 1–300 символов, объём — целое 1–500 или пусто (логическое значение
  числом не считается), названия одного уровня без повторов без учёта регистра.
  Итог проходит ту же схему `PlanContent`, что и сохранение версии плана.
- **Названия без номеров.** Нумерацию разделов («1.», «1.1.») добавляют показ плана,
  генерация текста и DOCX, поэтому в названиях её быть не должно: это требуют промпт
  и описание поля в схеме. Номер, который модель всё же поставила в начале названия
  («1. Введение», «1) Введение», «2.3. Структура», «2.3 Структура», «1.Введение»),
  убирается детерминированно, без повторного вызова модели и до проверки повторов
  названий. Числа внутри названия не трогаются («2024 год», «ISO 9001», «3D-модель»,
  «3.5 млн»); словесные префиксы («Глава 1», «Раздел 2») только запрещены промптом.
  Если от названия остался один номер, ответ не принимается (`invalid_response`).
- **Страницы.** Если в ТЗ задан объём, код распределяет его между разделами
  пропорционально предложению модели (метод наибольших остатков, минимум 1 страница
  на раздел, детерминированно): сумма равна объёму из ТЗ. Если разделов в ответе
  больше, чем страниц в ТЗ, такой план не принимается (`invalid_response`, повтор
  как у других невалидных ответов). Без объёма в ТЗ сохраняются значения модели. Общий объём считает код, а не модель.
  Раздел больше 8 страниц (`MAX_SECTION_PAGES` генератора) — в том числе после
  распределения — план не принимается (`invalid_response`, повтор); промпт сообщает
  модели этот предел и просит при большом объёме больше разделов (до 15).
- **Показ.** План экранируется и укладывается в 4096 символов: длинный план
  сокращается по шагам (сначала описания и требования, затем подразделы), все
  разделы остаются. Под планом — «Отменить заказ».
- **Дальше — подтверждение.** Под планом кнопки «Подтвердить план» и «Отменить
  заказ» (см. ниже); изменение и повторное составление плана — следующие этапы.
- **Повторы и лимиты.** Не больше 3 попыток за запуск и 6 вызовов модели на заказ
  (отдельно от анализа). Временная ошибка (лимиты, сбой сервера, сеть, обрезанный
  или невалидный ответ) — повтор в проходе восстановления; постоянная (запрос,
  ключ, отказ модели) или исчерпание попыток — шаг «ошибка» с кнопками «Повторить
  составление плана» и «Отменить заказ». Когда лимит вызовов исчерпан, остаётся
  только отмена. `max_tokens=16000`, тайм-аут и `effort` — как у анализа.
- **Восстановление.** Отдельный фоновый проход: первый — при запуске, дальше раз в
  60 с, до 5 заказов. Берёт заказы, ждущие повтора, зависшие попытки (дольше 10
  минут) и заказы, ждущие плана дольше минуты, — в том числе подтверждённые до
  появления этого шага.
- **Учёт и логи.** Каждый вызов — строка `llm_calls` (шаг `plan_generation`, без
  текста запроса и ответа); в `orders.error` — только код. В логи не пишутся план,
  ТЗ, материалы и параметры SQL: ошибки БД логируются только по типу.

## Подтверждение плана

На экране плана (`WAITING_FOR_PLAN_CONFIRMATION`) — кнопки «Подтвердить план» и
«Отменить заказ» (`app/bot/handlers/plan.py`, `app/services/plan_confirmation.py`).

- **Что происходит.** Под блокировкой заказа черновик плана становится
  подтверждённой (неизменной) версией, а заказ переходит в `PAYMENT_PENDING` — в
  одной транзакции: либо оба изменения, либо ни одного. Используются существующие
  `confirm_plan_version` (план построен на действующем подтверждённом ТЗ) и
  `change_status` (в `PAYMENT_PENDING` — только с подтверждённым планом). Черновик с
  разделом больше 8 страниц не подтверждается (`PlanSectionTooLargeError`: заказ и
  черновик не меняются, пользователю — «техническая ошибка»).
- **Устаревшая кнопка.** В кнопке — отпечаток плана (`content_digest`, как у
  подтверждения ТЗ): изменившийся после показа план не подтверждается, пользователь
  получает актуальный. Повторное нажатие — «План уже подтверждён», после отмены —
  «Действие уже неактуально»; БД не меняется.
- **Цена и оплата.** При переходе в `PAYMENT_PENDING` заказ получает цену в кредитах
  (см. «Кредиты и оплата»). После подтверждения бот показывает цену и баланс с
  кнопкой «Оплатить» или «Пополнить баланс» и «Отменить заказ». Пока заказ не оплачен
  и не отменён, он активен: «Новый отчёт», `/start` и обычный текст напоминают о нём.
- **Ошибки БД** логируются только по типу (без SQL, параметров и плана); при отказе
  транзакция откатывается до ответа в Telegram, об успехе сообщается только после
  commit.

## Генерация текста отчёта

Заказ в `GENERATING` (после оплаты кредитами) получает текст отчёта по
разделам подтверждённого плана через Anthropic (`app/services/report_generation.py`,
правила — `app/domain/report_generation.py`). Один шаг — один раздел вместе с его
подразделами: захват попытки и сохранение — короткие транзакции под блокировкой
заказа, вызов модели — без транзакции. Готовые разделы хранятся в
`order_report_sections` (одна строка на раздел версии плана, уникальность
`plan_version_id + section_index`), а не в `pipeline_state`. Когда все разделы
сохранены, заказ остаётся в `GENERATING`: DOCX и `COMPLETED` — отдельный шаг
(«Завершение отчёта»), затем «Доставка отчёта».

- **Вход модели.** Для каждого раздела — тот же полный вход, что при анализе и
  составлении плана: поля ТЗ без персональных данных (тема, вид, место и сроки
  практики, специальность, объём, дополнительные требования), подтверждённый план
  и тексты материалов (лимит 400 000 символов, те же теги), а также уже написанные
  разделы — каждый отдельным блоком. Названия разделов и подразделов модель не
  пишет: они берутся из плана.
- **Ничего не выдумывать.** Промпт запрещает выдумывать факты, даты, цифры,
  результаты практики, источники, литературу и цитаты. Все разделы проходят один и
  тот же механизм, без особых правил по названию. Список литературы пуст
  (`references = []`), титульного листа нет (`title_page = {}`) — отдельные этапы.
- **Ответ.** JSON Schema: номер раздела, абзацы раздела, абзацы подразделов. Код
  проверяет номер раздела, число подразделов по плану, непустой текст и объём.
- **Объём.** Страница — 1800 символов с пробелами; допуск — от 0,8 до 1,25 объёма
  раздела из плана (для 8 страниц — 11 520–18 000). Текст никогда не обрезается.
  Без объёма в плане проверяется только непустой текст. Вне допуска — одна
  немедленная регенерация с указанием фактического объёма и диапазона (новая
  попытка и новая строка `llm_calls`); снова вне допуска — `FAILED`
  (`size_out_of_range`). Хранимое состояние не помнит, что попытка была
  регенерацией: после сбоя или временной ошибки следующая попытка — обычная.
- **Ограничение: раздел не больше 8 страниц.** `MAX_SECTION_PAGES = 8` — лимит
  генератора (один ответ модели, `max_tokens=16000`, тайм-аут 300 с). План с таким
  разделом не принимается при составлении и не подтверждается, поэтому до оплаты не
  доходит; проверка в генераторе — последняя защита (например, для плана, сохранённого
  до этого ограничения). Раздел больше 8 страниц сразу завершает генерацию
  ошибкой `section_too_large` без вызова модели; автоматического деления раздела
  нет. Что 8 страниц укладываются в тайм-аут, проверяется замером на реальном API
  до релиза.
- **Лимиты.** Не больше 3 попыток подряд на раздел (счётчик обнуляется после
  сохранения раздела; зависшая попытка засчитана) и жёсткий бюджет 3 × N вызовов
  модели на весь отчёт (N — число разделов плана): в него входят регенерации,
  повторы, прерванные и зависшие вызовы. Бюджет проверяется по `llm_calls` под
  блокировкой заказа при захвате попытки.
- **Ошибки.** Постоянные — HTTP 400/401/403/404/413/422, ошибки клиента, отказ
  модели, нет подтверждённого плана или ТЗ, раздел больше 8 страниц: сразу
  `FAILED`. Временные — 408/409/429/5xx, тайм-аут, сеть, обрезанный или
  невалидный ответ: повтор в проходе восстановления, пока есть попытки и бюджет.
- **Кэш промпта.** Общий блок (ТЗ, план, материалы) одинаков для всех разделов и
  стоит первым; за ним — написанные разделы. Точки кэша (TTL 1 час) — на общем
  блоке и на последнем написанном разделе: `[A●][S1]…[Sk●][задание]`. Запись в
  кэш учитывается в `llm_calls.cache_creation_tokens`, чтение — в
  `cached_tokens`. Попадание в кэш (`cache_read_input_tokens > 0`) на втором и
  следующих разделах проверяется на реальном API до релиза.
- **Восстановление.** Фоновый проход `ReportGenerationRecovery`: первый — при
  запуске, дальше раз в 60 с, до 5 заказов, по одному следующему разделу на заказ.
  Попытка дольше 10 минут считается зависшей. Разделы одного заказа параллельно не
  генерируются.
- **Учёт и логи.** Каждый вызов — строка `llm_calls` (шаг `report_generation`, без
  текста запроса и ответа); в `orders.error` и логи — только коды, без текста
  разделов, ТЗ и материалов.

## DOCX-рендеринг отчёта

Готовые разделы превращаются в файл .docx чистой операцией, без БД, сети, LLM,
Telegram и хранилища: `assemble_document()` (Stage 3.1) → `DocumentContent` →
проверка → `PracticeReportDocxRenderer.render()` → байты. Жизненный цикл заказа на
этом шаге не меняется: сохраняет файл и завершает заказ отдельный шаг «Завершение
отчёта».

- **Контракт.** `DocumentContent` (`app/generation/schemas.py`) — общий для генерации
  и рендеринга, новой модели документа нет. Разделы и подразделы — названия из
  плана и абзацы текста.
- **Проверка** (`app/domain/report_document.py`, `validate_document_content`) — чистая
  функция, вход не меняет; рендерер вызывает её до создания документа (после
  проверок типа документа и своих возможностей). Не меньше одного раздела,
  глубина не больше двух (раздел → подраздел), непустые названия и абзацы, у
  раздела есть текст; без управляющих символов (в том числе переводов строк и
  табуляции), недопустимых в XML символов и суррогатов; лимиты: 300 заголовков,
  500 символов в названии, 2 000 000 символов в документе. Ошибка
  `InvalidDocumentError` несёт код и путь до места (`sections[1].paragraphs[2]`), но
  не текст. У `title_page` и `references` проверяются только данные: символы и общий
  лимит размера.
- **Возможности рендерера.** Поддержку титульного листа и списка литературы решает
  рендерер, а не общая проверка. DOCX-рендерер их пока не поддерживает: пустые
  `title_page` и `references` не выводятся, непустые отклоняются
  (`title_page_unsupported`, `references_unsupported`) до создания документа, а не
  теряются молча.
- **Оформление** (`app/rendering/docx.py`, python-docx) — ГОСТ 7.32-2017, все
  значения в одной константе `GOST_7_32`: A4, поля 30/15/20/20 мм, Times New Roman
  14, интервал 1,5, абзацный отступ 1,25 см, выравнивание по ширине, номер страницы
  внизу по центру (поле PAGE). Задаётся стилями Normal, Heading 1 и Heading 2; темы
  шрифтов и цвета шаблона python-docx заменяются явными значениями.
- **Структура.** «СОДЕРЖАНИЕ» с полем TOC (заголовки уровней 1–2), затем разделы,
  каждый с новой страницы. Нумерация «1.», «1.1.», «1.2.», «2.» — по положению
  раздела, а не по названию: «Введение» и «Заключение» тоже нумеруются (известное
  ограничение). Номер входит в текст заголовка и виден в оглавлении.
- **Оглавление — поле Word.** Номера страниц рендерер не считает: поле помечено к
  обновлению, Word заполняет его при открытии (с вопросом об обновлении полей),
  LibreOffice — при обновлении указателей. Реальное число страниц рендерер не знает;
  `CHARS_PER_PAGE = 1800` пока не перекалиброван. Строки оглавления оформлены явными
  встроенными стилями `toc 1` и `toc 2` (на основе Normal): без абзацного отступа, по
  левому краю, подраздел с отступом 1,25 см, номер страницы у правого края текста с
  точками.
- **Номер страницы и титульный лист.** Титульного листа пока нет, поэтому номер
  стоит на всех страницах, включая первую (оглавление). Будущий этап титульного листа
  должен включить `w:titlePg` и пустой нижний колонтитул первой страницы: титульный
  лист — страница 1 без номера, оглавление — страница 2 с номером.
- **Пакет без артефактов шаблона.** Из файла убраны части шаблона python-docx,
  которые не относятся к документу: миниатюра пустого шаблона, `docProps/app.xml`
  («Microsoft Macintosh Word», 0 слов), `customXml` (библиография со статичным GUID),
  `stylesWithEffects.xml` и `w14:docId`. Удаляются связи на них, поэтому
  `[Content_Types].xml` и `.rels` остаются согласованными. Нумерация списков, тема,
  таблица шрифтов, веб-настройки и `rsid` остаются: на них ссылаются стили шаблона,
  поэтому общий «отпечаток» шаблона python-docx полностью не убирается. Открытие в
  Word проверено; совместимость с LibreOffice (оглавление и очищенный пакет) пока не
  подтверждена.
- **Детерминизм.** Одинаковый документ — одинаковые байты: в свойствах файла только
  название (тема), без дат, автора и программы; у записей ZIP фиксированное время.
- **Синхронный рендерер.** `render()` занимает CPU: будущий async-код (сохранение
  файла и завершение заказа) обязан вызывать его через `asyncio.to_thread`, чтобы
  не блокировать цикл событий.

## Завершение отчёта

Когда сохранены все разделы плана, отдельный шаг (`app/services/report_completion.py`)
собирает документ, рендерит DOCX, сохраняет файл и переводит заказ в `COMPLETED`.
Генерация разделов этот шаг не запускает: его находит свой проход восстановления.

- **Транзакции.** Захват попытки — короткая транзакция под блокировкой заказа (все
  разделы есть, нет идущей попытки, лимит попыток), затем чтение разделов
  (`assemble_document`). Проверка документа, рендер (`asyncio.to_thread`) и
  `storage.save()` — без открытой транзакции и блокировок. Фиксация — снова под
  блокировкой и только если заказ всё ещё в той же попытке: строка
  `order_report_files` и `COMPLETED` — один commit. `COMPLETED` без сохранённого файла
  или при неполном наборе разделов невозможен.
- **Результат.** `order_report_files` — ключ, размер и SHA-256 файла; один файл на
  версию плана (уникальность `plan_version_id`). Ключ детерминированный:
  `orders/{order_id}/report/plan-{plan_version_id}.docx`. Повтор после сбоя между
  сохранением и commit пишет тот же ключ и те же байты (рендерер детерминирован).
- **Одновременная запись.** `LocalFileStorage.save()` пишет каждый раз в свой
  временный файл (`<имя>.<uuid>.tmp`) и атомарно заменяет им файл по ключу; при
  ошибке временный файл удаляется. Если зависшую попытку перехватили, пока старая
  ещё пишет, файл по ключу всё равно остаётся полным, а результат старой попытки
  отбрасывается при фиксации.
- **Ошибки.** Некорректный документ (`invalid_document:<код>`) или неполный
  (`incomplete_document`) — сразу `FAILED`. Сбой рендерера (`render_error`) или
  хранилища (`storage_error`) — повтор в проходе восстановления, всего 3 попытки,
  затем `FAILED` (`attempts_exhausted`). В `orders.error` пишется
  `report_completion: <код>`; в логи и ошибки текст отчёта не попадает.
- **Восстановление.** Фоновый проход `ReportCompletionRecovery` работает и без
  LLM-клиента: первый — при запуске, дальше раз в 60 с, до 5 заказов. Попытка дольше
  10 минут считается зависшей. Файл без строки (сбой после сохранения, затем
  `FAILED`) остаётся в хранилище; очистка — отдельная задача.

## Доставка отчёта

Готовый DOCX заказа в `COMPLETED` отправляется пользователю документом
(`app/services/report_delivery.py`; отправитель с `bot.send_document` — в
`app/bot/setup.py`). Статус заказа доставка не меняет: сбой доставки не делает заказ
`FAILED`.

- **Состояние.** `order_report_deliveries` — одна строка на файл отчёта (уникальность
  `report_file_id`, удаляется вместе с файлом): `attempts`, `started_at` (идёт
  попытка), `delivered_at`, `error` (код постоянной ошибки). Строки
  `order_report_files` по-прежнему только вставляются.
- **Транзакции.** Захват попытки — под блокировкой заказа (`COMPLETED`, файл
  действующего плана, не доставлено, без ошибки, нет идущей попытки, лимит). Чтение
  файла, сверка размера и SHA-256 со строкой файла и отправка — без открытой
  транзакции и блокировок; файл, не прошедший сверку, не отправляется. Фиксация —
  под блокировкой и только если строка доставки всё ещё в той же попытке.
- **At-least-once.** Если Telegram принял документ, а процесс упал до фиксации,
  попытка через 10 минут считается зависшей и повторяется: пользователь получит тот же
  файл второй раз. Это осознанно — доставка не теряется.
- **Ошибки.** Нет файла (`file_missing`) или он изменён (`file_corrupted`), бот
  заблокирован (`forbidden`), отказ Telegram (`bad_request`, `too_large`) — постоянные.
  Сбой сети или сервера Telegram и лимит запросов (`telegram_error`), сбой хранилища
  (`storage_error`) — повтор, всего 3 попытки, затем `attempts_exhausted`. В `error` и
  логи — только коды, без текста отчёта и `tg_id`.
- **Восстановление.** Фоновый проход `ReportDeliveryRecovery` работает и без
  LLM-клиента: первый — при запуске, дальше раз в 60 с, до 5 заказов.
- **«Мои заказы».** Под списком — кнопка «📄 Скачать отчёт #N» для каждого
  `COMPLETED`-заказа из списка (последние 10). Кнопка проверяет владельца и статус,
  сверяет файл с SHA-256 и отправляет его; работает сколько угодно раз и состояние
  фоновой доставки не меняет.

## Кредиты и оплата

Внутренняя единица — **кредиты**. Пользователь покупает кредиты за Telegram Stars
(валюта `XTR`) и оплачивает ими заказ. Это две разные операции
(`app/services/billing.py`, правила и прайс — `app/domain/billing.py`).

**Единицы.** Реальные деньги — только в `payments.amount` (Stars) и `payments.currency`.
Сколько кредитов даёт счёт — `payments.credits`. Баланс (`users.balance`), журнал
(`balance_transactions.amount`) и цена заказа (`orders.price`) — в кредитах.

**Прайс временный.** Пакеты (`CREDIT_PACKAGES`) и цены документов (`ORDER_PRICES`) в
`app/domain/billing.py` — значения для работы механизма. Экономика не утверждена,
до выпуска их нужно заменить.

- **Пополнение.** «💰 Баланс» → пакет → строка `payments` в `PENDING` (commit) →
  `sendInvoice` (payload `topup:<payments.id>` связывает счёт с этой строкой) →
  `pre_checkout_query` (только чтение: счёт свой, `PENDING`, не старше 24 часов,
  сумма совпадает) → `successful_payment` → одна транзакция: блокировка платежа,
  `SUCCEEDED` + `telegram_payment_charge_id` (нужен для возврата), блокировка
  пользователя, проводка `TOPUP` и `balance += credits`. Повторное подтверждение того
  же платежа ничего не меняет.
- **Сверка платежей.** Если звёзды списаны, а `successful_payment` не обработан (сбой
  процесса или БД), счёт остаётся `PENDING`. Проход `PaymentReconciliation` (при
  запуске и раз в 5 минут) ищет оплату таких счетов в `getStarTransactions` и
  подтверждает её тем же кодом — ровно один раз. API вызывается, только если есть
  `PENDING`-счета старше 2 минут и моложе 48 часов; не больше 20 страниц за проход;
  курсор позволяет не перечитывать историю (сбрасывается при рестарте или если
  порядок транзакций не хронологический).
- **Цена заказа.** Фиксируется при первом входе в `PAYMENT_PENDING` и больше не
  меняется: изменение прайса не влияет на оформленные заказы.
- **Оплата заказа.** «Оплатить N кредитов» → одна транзакция: блокировка заказа, затем
  пользователя; при нехватке кредитов ничего не меняется; иначе проводка
  `ORDER_CHARGE`, `balance -= price`, `PAYMENT_PENDING → PAID → GENERATING`. Генерацию
  подхватывает её проход восстановления. После пополнения кредиты сами не
  списываются: бот только предлагает кнопку оплаты.
- **Без оплаты генерации нет.** `change_status(PAID)` требует проводки `ORDER_CHARGE`
  заказа, а в `GENERATING` можно попасть только из `PAID`.
- **Журнал.** `balance_transactions` — источник истины, записи только добавляются;
  `users.balance` меняется только вместе с записью в журнал, и
  `users.balance == SUM(balance_transactions.amount)`. Ограничения БД:
  `CHECK (balance >= 0)`; уникальность `(order_id, reason)` — одно списание и один
  возврат на заказ; уникальность `payment_id` — одно зачисление на платёж;
  `(provider, provider_payment_id)` — один внешний платёж; знак суммы и ссылки
  согласованы с причиной (`ck_balance_transactions_reason_consistent`).
- **Блокировки.** Единый порядок: платёж → пользователь → заказ. Каждый апдейт бота
  начинается с обновления строки пользователя (`UserMiddleware`, блокировка до commit),
  и хендлеры заказа блокируют заказ после неё; оплата (`pay_order`) и возврат
  (`refund_failed_order`) делают так же — пользователь, затем заказ. Подтверждение оплаты фиксирует транзакцию апдейта до
  `confirm_topup` (платёж → пользователь, как у сверки). Внешних вызовов внутри этих
  транзакций нет.
- **Сбой после оплаты.** Генерация или завершение отчёта, упавшие в `FAILED`
  (`failed_from = GENERATING`), сами заказ не трогают. Проход `RefundRecovery`
  (`app/services/order_refunds.py`; при запуске, дальше раз в 60 с, до 5 заказов)
  вызывает `refund_failed_order`: одна транзакция под блокировками пользователь → заказ —
  проводка `ORDER_REFUND` на сумму **фактического** списания (а не `orders.price`),
  `balance += amount` и `FAILED → CANCELLED`. `change_status` не даёт отменить
  оплаченный заказ без `ORDER_REFUND`; второй возврат невозможен (статус под
  блокировкой и уникальность `(order_id, reason)`). После commit пользователь получает
  сообщение — best-effort: сбой Telegram возврат не отменяет. Заказ без списания не
  отменяется (только `logger.error`). Повтор генерации после сбоя не предусмотрен.
- **Не реализовано.** Возврат Stars (`refundStarPayment`) и ручной разбор отвергнутых
  подтверждений (о них — `logger.error` с номером платежа).
