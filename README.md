# tg-bot

Telegram-бот для генерации студенческих документов. Первый коммерческий сценарий —
**отчёт по практике в DOCX**.

Текущее состояние: регистрация пользователей, главное меню, оформление заказа с
приёмом материалов (PDF, DOCX, TXT) и извлечением из них текста. Генерация
документов, LLM, OCR, платежи и очередь задач пока не реализованы — для них
заложены интерфейсы.

## Требования

- Python 3.12+
- Docker Desktop (для PostgreSQL и Redis)
- Токен бота от [@BotFather](https://t.me/BotFather)

## Локальный запуск

PowerShell (Windows):

```powershell
# 1. Виртуальное окружение и зависимости
python -m venv .venv
.venv\Scripts\Activate.ps1
pip install -e ".[dev]"

# 2. Настройки: скопируйте пример и впишите BOT_TOKEN
Copy-Item .env.example .env

# 3. PostgreSQL и Redis
docker compose up -d

# 4. Миграции
alembic upgrade head

# 5. Бот
python -m app.main_bot
```

В bash/zsh отличаются только активация окружения (`source .venv/bin/activate`)
и копирование файла (`cp .env.example .env`).

## Тесты и линтер

```powershell
docker compose up -d      # тестам нужен PostgreSQL
pytest
ruff check .
ruff format --check .
```

Тесты работают на отдельной БД `tg_bot_test` (создаётся `docker/postgres/init.sql`
при первом запуске контейнера). Перед прогоном схема пересоздаётся миграциями
(`downgrade base` → `upgrade head`), каждый тест выполняется в транзакции, которая
откатывается. `tests/test_migrations.py` проверяет, что модели и миграции не расходятся.

> Если том `postgres_data` был создан до появления `init.sql`, тестовой БД не будет.
> Создайте её вручную:
> `docker compose exec postgres createdb -U tg_bot tg_bot_test`

## Миграции

```powershell
alembic revision --autogenerate -m "описание"   # после изменения моделей
alembic upgrade head
alembic downgrade -1
```

Сгенерированную миграцию всегда просматривайте вручную. Новое значение
PostgreSQL enum (например, новый тип документа) добавляется миграцией с
`ALTER TYPE ... ADD VALUE`.

Тесты извлечения текста стоит прогонять и в Linux-контейнере (это целевая среда;
версии libxml2 в колёсах lxml для Windows и Linux разные, и коды ошибок у них
тоже). Из каталога проекта, при запущенном `docker compose up -d`:

```bash
docker run --rm --network tg_bot_default -v "$PWD:/src:ro" python:3.12-slim bash -c '
  cp -r /src /work && cd /work && rm -rf .venv &&
  pip install -q -e ".[dev]" &&
  TEST_DATABASE_URL=postgresql+asyncpg://tg_bot:tg_bot@postgres:5432/tg_bot_test pytest -q'
```

## Извлечение текста из материалов

После приёма файла бот в том же апдейте извлекает из него текст и сообщает
результат отдельным сообщением. То, что там не удалось или не случилось,
подбирает восстановление (см. ниже) — без участия пользователя.

- **Изоляция.** Разбор выполняется в отдельном дочернем процессе
  (`python -I -m app.extraction.worker`) с минимальным окружением: секретов бота
  в нём нет. Жёсткий тайм-аут 30 с, после него процесс снимается и дожидается
  завершения; stdout читается с потолком 8 МиБ. Одновременно работает один процесс.
  На Linux процессу ставятся `RLIMIT_AS` (`EXTRACTION_MEMORY_LIMIT_MIB`, по
  умолчанию 1024 — экспериментальное значение) и `RLIMIT_CPU` 35 с; на Windows
  ограничения памяти нет.
- **PDF** — pypdfium2 (PDFium). **DOCX** — lxml, без python-docx. **TXT** —
  UTF-8, UTF-16 с BOM, cp1251.
- **Лимиты:** 500 000 символов на материал; первые 300 страниц PDF; мягкий бюджет
  20 с (дальше — частичный результат); DOCX: одна XML-часть до 16 МиБ, всего
  распаковывается не больше 64 МиБ, частей в архиве не больше 1000, сумма
  заявленных размеров не больше 256 МиБ.
- **Хранение.** Текст — в `order_material_texts` (NFC, переводы строк `\n`,
  страницы PDF разделены `\f`). У материала: статус, машиночитаемая причина
  сбоя `failure_reason`, число попыток, момент начала обработки.
- **Пустой текст — не ошибка:** материал обрабатывается с пометкой «текста нет».
  «Похоже на скан» (на странице только изображения) и «текст может быть
  извлечён неверно» — эвристики, а не причины отказа.
- **Повторы** — только для временных сбоев (хранилище, запуск процесса,
  прерванная обработка, временная ошибка БД при сохранении результата), не больше
  3 попыток; попытка расходуется только при взятии материала в обработку.
  Повреждённый, зашифрованный файл, тайм-аут, аварийное завершение и отказ БД
  принять результат не повторяются: пользователь присылает файл заново. Файл
  материала обработка только читает и при сбоях не трогает.
- **Ошибки БД при сохранении результата** классифицируются по SQLSTATE
  (`app/db/errors.py`): ошибки данных, ограничений и лимитов (`22*`, `23*`, `54*`)
  — `result_rejected`, без повтора; соединение, deadlock, сериализация, нехватка
  ресурсов, тайм-аут запроса и нераспознанные ошибки — `database_error`, с
  повтором. Код и тип ошибки сохраняются в `processing_error` (без текста документа).

### Восстановление обработки

Внутри процесса бота работает проход восстановления
(`app/services/material_recovery.py`): первый — сразу при запуске, дальше раз в
60 с (`RECOVERY_INTERVAL_SECONDS`), не больше 10 материалов за проход
(`RECOVERY_BATCH`), начиная с самых старых. Он берёт материалы заказов, которые ещё
принимают файлы:

- `RECEIVED` старше 2 минут (`RECEIVED_GRACE`) — свежие обрабатывает сам апдейт;
- `PROCESSING` дольше 3 минут (`STALE_PROCESSING_AFTER`) — прерванная обработка;
  после рестарта более свежий `PROCESSING` не трогается, пока порог не истечёт;
- `FAILED` с повторяемой причиной, пока не исчерпаны попытки.

Материал обрабатывается тем же кодом, что и в апдейте; двойной захват исключают
блокировка строки и номер попытки. Очередь извлечения общая: если она занята,
проход заканчивается и продолжается в следующем. Срок обработки не гарантируется —
при большом числе материалов они ждут очереди. Пользователь получает сообщение об
окончательном исходе (текст извлечён или повтора не будет) после фиксации в БД,
не больше одного раза; если процесс упадёт между фиксацией и отправкой, сообщения
не будет. Интервал и размер прохода — константы в коде, не настройки.

Ограничения полноты:

- нет OCR: из сканов и картинок текст не извлекается;
- DOCX: не извлекаются сноски, концевые сноски, комментарии, SmartArt и
  диаграммы; текст надписи выводится перед абзацем, в котором она стоит;
  документы с `DOCTYPE` отклоняются;
- PDF: многоколоночная вёрстка читается построчно поперёк колонок; разделение
  «скан» и «шрифт без ToUnicode» — эвристика;
- обработка рассчитана на один экземпляр бота (polling). При нескольких
  экземплярах один материал дважды не захватывается (блокировки строк в
  PostgreSQL), но у каждого экземпляра своя очередь и свой дочерний процесс
  извлечения: одновременно может работать по процессу на экземпляр;
- прерванная обработка (например, рестарт во время извлечения) расходует попытку:
  частые рестарты могут исчерпать 3 попытки.

Лицензии встроенных библиотек — в [THIRD_PARTY_NOTICES.md](THIRD_PARTY_NOTICES.md).

## Структура

```
src/app/
├── config.py            # настройки из .env
├── main_bot.py          # точка входа бота
├── bot/                 # Telegram-слой: хендлеры, клавиатуры, middleware, тексты
├── domain/enums.py      # доменные перечисления
├── db/                  # модели SQLAlchemy, сессии, классификация ошибок БД
├── extraction/          # извлечение текста: дочерний процесс, PDF, DOCX, TXT
├── services/            # бизнес-логика без зависимости от Telegram
│   ├── users.py
│   ├── order_materials.py, material_processing.py, material_recovery.py
│   ├── payments/base.py # интерфейс платёжного шлюза
│   └── storage/         # интерфейс файлового хранилища + локальная реализация
├── llm/base.py          # интерфейс LLM-клиента
├── generation/          # контракт DocumentContent + интерфейс генератора
└── rendering/base.py    # интерфейс рендерера (DocumentContent → файл)
```

Слой `bot/` вызывает `services/`, а генерация и рендеринг не знают про Telegram.
Новый тип документа добавляется как новые генератор и рендерер без изменения ядра.

## Деньги и баланс

- Все суммы хранятся в целых копейках.
- `balance_transactions` — журнал операций и **источник истины**; записи только добавляются.
- `users.balance` — денормализованный кэш суммы журнала. Он меняется только в той же
  транзакции БД, что и запись в журнал. Ограничение `CHECK (balance >= 0)` не даёт уйти в минус.
- Уникальный индекс `(order_id, reason)` не допускает двойного списания или возврата по заказу,
  уникальность `(provider, provider_payment_id)` — повторного зачисления одного платежа.
